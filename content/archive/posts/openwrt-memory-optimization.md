路由器内存优化，最常见的误区是：**看 `free` 说"还有"，就以为够了；或者听供应商说"只占这么多"，就信了。**

真实做法是反过来：**先定方向，再逐项追查，最后用可复现的指标验证。** 下面是我用的一套顺序。

> 说明：只讲公开方法，不涉及任何具体产品或内部实现。

## 1. 先砍"不该在路由上的东西"

路由器的本质是**转发 + 接入 + 管理**，不是通用计算平台。所以第一步是**大方向裁剪**：

- **Java / Python 这类运行时**：如果没有业务强依赖，**整条链去掉**（运行时 + 库 + 相关包）。
- 桌面/图形、没用到的语言包、调试工具、文档。
- 用不到的协议栈/驱动模块。

```bash
# 看谁在占空间/装了什么
opkg list-installed | sort
du -sh /usr/lib/* 2>/dev/null | sort -h | tail
```

**原则**：不是"能不能跑"，是"**该不该在这台设备上**"。

## 2. 追"保留内存"——但别轻信供应商

芯片平台通常有一块**保留内存**（TEE、modem、DSP、多媒体、安全域等），这部分**在 `free` 里看不到，但确实被占着**。

做法：
1. 向芯片供应商要**内存布局**（reserved regions / memory map）；
2. **自己验证**：
```bash
cat /proc/iomem
cat /proc/meminfo
dmesg | grep -i -E 'reserved|memory'
# 设备树里的 reserved-memory
```
3. 对照"供应商说的"和"实际量的"，**对不上就问、就查**。

> **关键态度**：供应商的数字是"参考"，不是"真相"。**保留内存放哪了，必须自己核一遍。**

## 3. tmpfs：看不见的"大头"

`tmpfs` 是**内存文件系统**——写进去的东西占的是 RAM，不是 Flash。

```bash
mount | grep tmpfs
df -h            # 看 tmpfs 挂载点大小
du -sh /tmp /var /run 2>/dev/null
```

常见可裁的地方：
- `/tmp`、`/var`（OpenWrt 里 `/var` 常指向 `/tmp`）——日志、缓存、临时文件；
- 把日志/缓存改到**有 Flash 的分区**或**限制大小**；
- 通过挂载参数限制 `size=`，避免 tmpfs 无限吃内存。

**能裁就裁**：tmpfs 是"看起来没进程、其实很能吃"的典型。

## 4. ZRAM：用时间换空间

`ZRAM` 把一部分内存做成**压缩的交换区**：写进去的页先压缩，**用 CPU 换内存**。

```bash
# 一般装 zram-swap
opkg install zram-swap
# 看设备与压缩情况
zramctl
cat /proc/swaps
```

**本质**：不是"免费内存"，是**用压缩/解压的 CPU 时间，换出更多可用空间**。

适用：
- 内存吃紧、CPU 有余（很多路由 CPU 并不满）；
- 冷数据多（日志、缓存）时收益明显。

注意：
- 压缩率取决于数据（文本/日志高，已压缩数据低）；
- 会**增加 CPU 与延迟**，实时性敏感的业务要评估。

## 5. 用 smaps 的 **PSS** 验证，别信 RSS

这是最容易被骗的一步。看进程内存，很多人只看 RSS——**RSS 会把共享页重复计算**（同一个库被 10 个进程映射，RSS 就记 10 次）。

三个指标：
- **RSS**：常驻页（**含共享，会重复计数**）；
- **PSS**：共享页按"共享者数量"**平摊** + 私有页 → **最能反映"真实占用"**；
- **USS**：只算**私有页**（进程独占）。

```bash
# 单进程
cat /proc/<pid>/smaps | grep -E '^(Rss|Pss|Private)' 
# 汇总（很多系统有 smem / procrank）
smem -t -k
```

**做优化、做报表，用 PSS**；RSS 只能当参考，**它经常骗人**。

## 一句话

> **内存优化不是"删包 + 调参数"，是"定方向 → 追保留内存 → 查 tmpfs → 上 ZRAM → 用 PSS 验证"。**

数字要自己量，供应商的话要自己核。**你信的东西，决定你最后省下多少。**
