## 现实：很多项目没有 benchmark 条件

理想情况是：同一块板、三套算法、跑同一负载、量压缩比/CPU/延迟。
现实往往是：**样机不够、时间不够、业务不能停、没有合适工具**。

那怎么办？**不能因为没数据就不决策，也不能拍脑袋。** 我的做法是**三路交叉**：

1. **供应商意见**——他们最懂自家 SoC；
2. **理论评估**——压缩比与 CPU 的基本关系；
3. **竞品对照**——同价位产品怎么选。

三路指向一致，就敢定；不一致，就标为风险，上线后重点验证。

## 路一：供应商意见（但要交叉验证）

芯片/方案商通常知道：

- 自家 CPU 的**算力与功耗**（压缩是 CPU 活）；
- 默认 BSP 里 **zram 的算法/大小**；
- 目标场景（网关/CPE/低端）**推荐的默认值**。

**怎么问**：不要只问"推荐哪个"，要问"**为什么**"——是 CPU 余量、还是延迟、还是他们踩过坑。

**但要交叉验证**：供应商的"推荐"可能是"通用默认"，不一定适配你的**负载**。他们的意见是**权重很高的输入**，不是结论。

## 路二：理论评估（不用跑也能估个大概）

几个基本事实，足以支撑初选：

- **压缩比**：文本/日志/零页 → 高；已压缩数据（图片/加密）→ 低；
- **CPU 成本**：`lz4` 最快，`lzo/lzo-rle` 次之，`zstd` 压缩比最高但更吃 CPU；
- **延迟**：换页是同步路径，**压缩越重，抖动越大**；
- **收益边界**：数据本身不可压时，ZRAM 基本是"白烧 CPU"。

**推论**（不是绝对）：
- **弱 CPU / 延迟敏感** → 偏 `lz4` / `lzo-rle`；
- **CPU 有余 / 内存紧 / 冷数据多** → 偏 `zstd`。

## 路三：竞品对照（看别人怎么选）

拆机或看公开固件，能看到**同价位产品**的选择：

```bash
# 竞品/参考设备上（只读）：
cat /sys/block/zram0/comp_algorithm     # 当前算法（方括号里是选中的）
cat /sys/block/zram0/disksize           # zram 大小
cat /proc/sys/vm/swappiness             # 换页倾向
zramctl                                 # 压缩率（跑起来后）
```

看三件事：**算法、大小、swappiness**。
- 同定位产品**都选同一档** → 说明这是"够用且稳"的默认；
- 有人用更激进的配置 → 看它的 CPU/内存档位，判断你是否具备同样条件。

> 注意：只做**公开资料/只读分析**，别碰别人的私有实现与法律红线。

## 三路交叉 → 决策矩阵

| 你的条件 | 倾向 |
|---|---|
| CPU 弱、业务延迟敏感 | `lz4` / `lzo-rle`，zram 别开太大 |
| CPU 有余、内存紧、冷数据多 | `zstd`，可适度开大 |
| 不确定 | **跟随同档竞品的稳定配置**，标为待验证 |

**原则**：先选"**最不容易翻车**"的配置，而不是"理论最优"。

## 关键：上线后用最小成本验证

没数据不等于永远没数据。上线后花很小代价补：

```bash
zramctl                  # 压缩率
vmstat 1 5               # si/so 是否频繁
cat /proc/meminfo        # SwapTotal/Free
# 再看业务侧：CPU 占用、关键请求延迟
```

**判据**：
- `si/so` 长期为 0 → 配置够用，别再加；
- 频繁换页 + CPU 飙高 → 压过头，换更快的算法或调小 zram；
- 结合 **PSS**（不是 RSS）看真实占用。

## 一句话

> **没数据时，靠"供应商 + 理论 + 竞品"三路交叉做决策；上线后，用最小成本把"假设"变成"数据"。**

决策可以没有 benchmark，但**不能没有验证计划**。
