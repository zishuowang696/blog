## 我判断一套嵌入式框架好不好，只看一件事

> **不看代码，只看配置，你能不能说清"这个程序在干什么"？**

大多数 C 项目做不到。"程序在干什么"散落在：到处 `include` 的头文件、手工拼装的初始化、重复定义的设备状态、只有作者看得懂的 list/hash。

而**可读性，最后都落到"配置"上**：

- 配置能说清**结构**；
- 结构能说清**意图**；
- 意图清楚了，**维护和排错才不靠"问作者"**。

这就是我后来看到 AMX 时最在意的一点——它把"程序在干什么"**摆到了明面上**。

## 写 C 久了，会发现一个隐痛

C++ 有 STL，Java 有集合，Go 有 map/slice。C 呢？链表、哈希、动态数组、变长字符串——**每个项目自己写一遍**。

写一遍不算难，难的是：

- 每个项目的实现风格都不一样；
- 内存、对齐、所有权、迭代器失效……坑一个不少；
- 换一个项目，代码**不能直接复用**；
- 出了问题，**只有写它的人能修**。

## 于是我去找「C 的容器」

我找了很多年。看过各种库，也自己写过一版。

自己写的结果是：**能跑，但效果不理想。**

后来我想明白了原因：

> **容器库只是一个"零件"。真正难的不是零件，是"零件怎么装成一台机器"——组件怎么找到彼此、怎么描述自己的状态、怎么被装配、怎么被远程调用。**

一个再好的 list/hash 库，也解决不了这些。

## 我的一个判断

这些年我越来越确信一件事：

> **如果 OpenWrt 这类系统能用上"容器化"的框架，至少能省掉 80% 的重复工作量。**

（这是我的判断，不是精确统计。但只要你写过几个组件、接几次总线、重复定义几遍数据模型，你大概会同意。）

你要的不是把 `void*` 塞进链表，而是：

- 组件有**统一的描述**（对象、参数、接口）；
- 组件能被**装配**（配置化，而不是硬编码）；
- 组件之间通过**总线**通信，而不是互相 `include`；
- 换一个平台/总线，**业务代码不用改**。

## 直到我在 prplOS 里看到 AMX

第一次看到 **AMX（Ambiorix）**，我的感觉是：**它来了。**

因为它不是"又一个 C 的 list/hash 库"，它是：

- **`libamxc`**：容器（List / Hash / Variant）；
- **`libamxd`**：数据模型（对象 / 参数 / 函数）；
- **`libamxb`**：总线抽象（ubus / D-Bus）；
- **`libamxo`**：用 ODL 把对象树**装配**起来；
- **`libamxrt`**：组件的**运行时与生命周期**。

**它把"容器"做成了"系统骨架"。** 这正是我找了多年、却一直没找到的那一层。

> **AMX 不只是 prpl 的：它的容器（List / Hash / String / Variant）可以直接用在你的 C 项目里。**
>
> **纯 C（C11），不需要 C++ 运行库；`libamxc.so` strip 后约 187K，只依赖 libc。**

## 它到底省什么：工作量，和可读性

**先说省工作量：**

- **容器不用重写**：List/Hash/Variant 是现成的，不用每个项目再来一遍；
- **组件不再互相 `include`**：通过总线找对方，少了一大堆头文件耦合；
- **数据模型用 ODL 声明**：不用把"设备有哪些状态"散落在各处代码里；
- **换总线不改业务**：ubus / D-Bus 换了，业务组件不动。

**再说可读性——我觉得它比"省工作量"更重要。标准只有一条：一眼配置，就知道程序在干什么。**

- **统一的数据模型**（对象 / 参数 / 函数）：代码开始"自解释"，看对象树就知道这个组件能干什么；
- **配置与代码分离**：ODL 把结构摆在明面上，比在 C 里到处 `if/else` 拼装好读得多；
- **组件边界清晰**：每个模块更小、职责更单一，读一个文件不用跳十个文件；
- **路径/命名统一**：对象路径是标准的、可预测的，调试和排查时心里有数。

> **省工作量，是"少写"；可读性，是"好维护"。前者省的是开发时间，后者省的是后来所有人的时间。**

## 所以我决定：把它搞懂

我承认，看到 AMX 的时候有点激动。不只是因为它"能用"，而是因为它**把我脑子里那套模糊的东西，用 C 实打实地做出来了**。

所以这个系列，是我的学习笔记：

- 它不只是抄文档，而是**我理解它的过程**；
- 我会写它的**容器、数据模型、总线、装配、生命周期**；
- 也会写它**不是什么**——别把它当纯 DI 框架。

## 写给和我一样找了很久的人

如果你也写过一堆 `list.c` / `hash.c`，也为"组件怎么解耦"头疼过，也自己造过轮子——

**AMX 值得你认真看一遍。**

不是因为它完美，而是因为它回答了一个很老的问题：

> **C 也能有"容器化的系统骨架"，而且已经在跑。**
