## 一个困扰我很多年的问题

写 C 久了，会发现一个隐痛：**C 没有标准容器。**

C++ 有 STL，Java 有集合，Go 有 map/slice。C 呢？链表、哈希、动态数组、变长字符串——**每个项目自己写一遍**。

写一遍不算难，难的是：

- 每个项目的实现风格都不一样；
- 内存、对齐、所有权、迭代器失效……坑一个不少；
- 换一个项目，代码**不能直接复用**；
- 出了问题，**只有写它的人能修**。

## 于是我去找「C 的容器」

我找了很多年。看过各种库，也自己写过一版。

自己写的结果是：**能跑，但效果不理想。**

后来我想明白了原因：

> **容器库只是一个"零件"。真正难的不是零件，是"零件怎么装成一台机器"——组件怎么找到彼此、怎么描述自己的状态、怎么被装配、怎么被远程调用。**

一个再好的 list/hash 库，也解决不了这些。

## 我的一个判断

这些年我越来越确信一件事：

> **如果 OpenWrt 这类系统能用上"容器化"的框架，至少能省掉 80% 的重复工作量。**

（这是我的判断，不是精确统计。但只要你写过几个组件、接几次总线、重复定义几遍数据模型，你大概会同意。）

你要的不是把 `void*` 塞进链表，而是：

- 组件有**统一的描述**（对象、参数、接口）；
- 组件能被**装配**（配置化，而不是硬编码）；
- 组件之间通过**总线**通信，而不是互相 `include`；
- 换一个平台/总线，**业务代码不用改**。

## 直到我在 prplOS 里看到 AMX

第一次看到 **AMX（Ambiorix）**，我的感觉是：**它来了。**

因为它不是"又一个 C 的 list/hash 库"，它是：

- **`libamxc`**：容器（List / Hash / Variant）；
- **`libamxd`**：数据模型（对象 / 参数 / 函数）；
- **`libamxb`**：总线抽象（ubus / D-Bus）；
- **`libamxo`**：用 ODL 把对象树**装配**起来；
- **`libamxrt`**：组件的**运行时与生命周期**。

**它把"容器"做成了"系统骨架"。** 这正是我找了多年、却一直没找到的那一层。

## 所以我决定：把它搞懂

我承认，看到 AMX 的时候有点激动。不只是因为它"能用"，而是因为它**把我脑子里那套模糊的东西，用 C 实打实地做出来了**。

所以这个系列，是我的学习笔记：

- 它不只是抄文档，而是**我理解它的过程**；
- 我会写它的**容器、数据模型、总线、装配、生命周期**；
- 也会写它**不是什么**——别把它当纯 DI 框架。

## 写给和我一样找了很久的人

如果你也写过一堆 `list.c` / `hash.c`，也为"组件怎么解耦"头疼过，也自己造过轮子——

**AMX 值得你认真看一遍。**

不是因为它完美，而是因为它回答了一个很老的问题：

> **C 也能有"容器化的系统骨架"，而且已经在跑。**
