# 最小可发版本（MVP）——忙到极点怎么"不断更"

> 底线不是"发得多好"，而是**不断更**。有料就发大，没空就发小；**宁可小，不可断**。

| 类型 | 正常版本 | **MVP（最省力）** |
| --- | --- | --- |
| 长文 / YouTube | 完整实测 + 剪 | 300 字"我解决了什么 + 一个数字 + 结论" |
| 短视频（抖音） | 分镜 + 配音 + 字幕 | **一张对比图 + 一句结论**（15s，打字幕即可） |
| GitHub | Release + 文档 | 一个 commit + README 加一句话 |
| 存在感 | — | 一条推文 / 一张截图 / 一段日志 |

## 触发规则（自动降级，不纠结）
- 当天有 2 小时 → 做正常版本；
- 只有 20 分钟 → 直接发 **MVP**，别等"以后做完整版"（大概率永远不做）；
- 连续忙 → 从「缓冲池」取一条发，制造缓冲所需的时间靠**批量日**补。

## 三类内容的最省力发法（可直接套）
1. **解释型**（如 nvcc/GCC）：**一张流程图 + 3 句结论**，抖音 15–30s 就够；
2. **实测型**（如量化/功耗）：**一张数据表 + 一句"所以呢"**，长文再慢慢补；
3. **避坑型**（如 Pi5+Hailo）：**一句反转 + 一个理由**，天生适合 MVP 短内容。

## 一条铁律
> **发布永远从 `topics.md` 取，素材永远在 `capture-log.md` 里。**
> 忙，只会让你"发得小"，不会让你"没得发"。
